## P1 / решение владельца. Один чемпионат имеет разные периоды допуска, результатов и призов

**Файлы:**

- `backend/app/services/event.py:689-752`
- `backend/app/services/event.py:666-686`
- `backend/app/models.py:75-106`

`real_entries()` формирует сезонные записи, но использует:

```python
pnl = float(led.contest_pnl) if led else 0.0
ret = float(led.return_pct) if led else 0.0
```

`DayLedger` — ledger только текущих календарных суток. Поэтому рейтинг A/B зависит от результата сегодня, а допуск — от депозита за сезон. **Это соответствует текущему `event_rules` (строки 45–46), но расходится с README и `/rules`**, где требуется депозит сегодня. `/rating` при этом называется метриками «того же чемпионата».

Например, вчерашний депозит `$50` даёт event-допуск сегодня, но не даёт дневной допуск; без сегодняшнего qualifying deposit `poll.py` обнуляет PnL. На главной участник уже «в рейтинге», а в дневном контуре ещё не участвует. Изменение `event_min_deposit` независимо от `min_day_deposit` усиливает расхождение.

Дополнительно `prize_pool/prize_table` обещают `$5000` на 10 мест, тогда как `freeze_day()` использует отдельные дневные `[100, 50, 25]` и компенсации. Обработчика присуждения/архива сезонных призов в коде нет. Это может быть ручной процесс, но он не обозначен.

### Что исправить

1. Выбрать модель: дневной чемпионат; накопительный сезон; либо сезонный допуск с ежедневными результатами.
2. Для последнего варианта сохранить дневные результаты, но отделить ежедневную стартовую точку от требования нового депозита каждый день.
3. Только если выбран накопительный сезон — реализовать сезонные snapshots/PnL/basis и отдельные результаты.
4. Установить связь публичной призовой таблицы с реальным присуждением либо явно назвать её отдельным сезонным/ручным фондом.
5. Генерировать правила из согласованной конфигурации. Сейчас текст «от $50» в `event_rules` не меняется вместе с настройкой.
6. Приёмка: один UID с депозитом вчера и сегодня должен получать объяснимые и согласованные статусы на главной, `/rating`, `/rules`, в Telegram и архиве.

## P0. Номинация B сезонного ивента считает вывод как потерю

**Файлы:**

- `backend/app/services/event.py:721-749`
- `backend/app/services/event.py:258-298`
- `backend/app/ledger.py:54-70`

Дневная логика намеренно разделяет:

- `contest_pnl` — вывод снижает результат;
- `trading_pnl` — вывод добавляется обратно, это чистый торговый PnL.

Дневная номинация B использует `trading_pnl`, что соответствует правилу «нельзя нарисовать убыток выводом».

Но сезонный `real_entries()` передаёт в event board только `led.contest_pnl`. Поэтому участник, который заработал, а затем вывел деньги, может получить отрицательный `contest_pnl` и попасть в сезонный топ потерь. Это противоречит дневной логике и тексту правил.

### Что исправить

Использовать отдельные поля `contest_pnl` и `trading_pnl` в event-представлении. Период расчёта оставить согласованным с регламентом, не менять его автоматически:

- A сортировать по `return_pct` соответствующего периода;
- B включать только отрицательный `trading_pnl` того же периода;
- показывать в B абсолютную чистую торговую потерю.

Добавить regression-тест: прибыль + вывод не попадает в номинацию B.

## P0. Неверно выбирается стартовый snapshot при позднем депозите

**Файлы:**

- `backend/app/ledger.py:25-43`
- `backend/app/services/poll.py:137-181`

Если до первого snapshot внесена только часть qualifying deposit, а остаток внесён позже, код может вернуть первый snapshot как стартовый:

```python
if stats_depo >= min_dep:
    return opening
```

Пример:

1. До 12:00 участник внёс `$30`, lifetime `sum_deposits` стал `530`.
2. 12:00 первый snapshot: `sum_deposits=530`.
3. 13:00 участник внёс ещё `$20`; второй snapshot: `sum_deposits=550`.
4. API statistics показывает дневные `50`.
5. Разница относительно opening равна `20 < 50`; fallback выбирает snapshot 12:00, до достижения порога.

В результате торговый результат до достижения qualifying deposit входит в PnL участника, хотя правило говорит «старт после депозита». Локальная проба `pick_start_snapshot([530,550], 50, 50)` вернула первый snapshot.

**Не перепутать:** если полный депозит `$50` пришёл после opening и отражён следующим snapshot, существующий цикл корректно выбирает следующий snapshot. Ошибка — в смешанном/недостаточно наблюдаемом случае.

Комментарий функции утверждает, что депозит уже был внутри первого snapshot, но код этого не проверяет.

### Что исправить

- Не использовать текущую агрегированную статистику как доказательство того, что депозит был до первого snapshot.
- Разделить случаи:
  - qualifying deposit доказан на момент первого snapshot — использовать первый;
  - депозит появился позже — использовать первый snapshot, где достигнут порог;
  - точного момента нет — участник остаётся вне зачёта до подтверждения.
- Добавить тест на поздний депозит.

## P2. Админка неправильно считает остаток призового фонда

**Файл:** `web/components/EventPanel.tsx:161-165,526-532`

В default `prize_table` строка `6–10 места` означает `$180` **каждому** из пяти мест. Реальная сумма:

```text

```

## P1. Partners limiter ждёт почти минуту при секундном ограничении

Также limiter отдельный в процессах API/worker и не координирует общую квоту одного токена.

**Тесты:** секундный лимит без минутного; минутный без секундного; пять 429; два потребителя одного токена. Фактическую общую квоту подтвердить у провайдера, не менять числа по предположению.

## P1. Season cache не привязан к конфигурации периода

## P2. Settings/showcase допускают нечисловые и неконсистентные значения

## Дополнительные риски, которые нужно проверить отдельно

Это не доказательства произошедшей аварии и не повод менять бизнес-правила без согласования:

- **Свежесть данных.** `snapshot_uid()` при пустом ответе просто возвращает `None`, сохраняя старый eligible ledger; `freeze_day()` не проверяет возраст. Нужны `last_success_at`, stale/error state и политика участия при недоступности API.
- **Контракт Partners.** `_point_from_info()` превращает отсутствующие денежные поля в нули; `bool("false")` даёт `True`, а строковый/числовой `status` не нормализуется. Нужна строгая входная модель на основании **реального** контракта API; не утверждать, что API действительно присылает такой формат, без fixture. Особенно проверить, входят ли открытые ставки, бонусы и отменённые выводы в balance/counters.
- **Округление компенсации.** `loss_compensation()` не округляет выплату до центов; БД хранит 4 знака, Telegram показывает 2. Например, `15%` от `$0.01` равны `$0.0015`. Согласовать денежное округление и хранить уже окончательную выплату.
- **Время обновления ledger.** `DayLedger.updated_at` имеет только `server_default`, не обновляется при изменении. Не использовать его как время свежей проверки без явного обновления.
- **Startup гонка.** API и worker одновременно выполняют `init_db()`, `get_settings()` и `ensure_showcase()`; проверки «нет строки — вставить» не атомарны. Нужны migration/init lock и integration-тест пустой БД с обоими процессами.
- **Доставка final.** Нет транзакционного outbox/уникального идентификатора публикации: crash после успешной отправки до `job_set()` может создать дубль. Повторная публикация должна быть управляемой, с сохранением message ID.
- **Публичные данные.** `/public/trader/{uid}` и архив возвращают Telegram, country, balances/cashflow без авторизации, а UID раскрываются в board. Уточнить, какие поля участник согласен публиковать; ограничить не относящиеся к рейтингу персональные/финансовые сведения.
- **Deployment.** В `config.py` есть известный fallback admin token, а server-compose сам по себе публикует HTTP без TLS. Требуется fail-fast при дефолтном токене и TLS на доверенном proxy. Это не утверждение, что реальный production использует дефолт.
- **Настройки-мёртвые поля.** `stats_players`, `stats_turnover`, `activity` принимаются SettingsPatch, но public event вычисляет/берёт другие значения. Удалить/переименовать либо объяснить, где эти настройки применяются.
- **Две выключенные номинации.** `visible_nominations(False, False)` возвращает `(True, True)`; это закреплено тестом и поясняется frontend. Не «исправлять» в пустой экран автоматически, а согласовать семантику переключателей.
- **Обновление таблицы frontend.** В `Board.tsx` нет отмены предыдущего fetch при смене A/B: медленный старый ответ может заменить новый board. Добавить request version/AbortController и тест обратного порядка ответов.
- **Масштабирование опроса.** Watchlist последовательно обходит всех участников, перечитывая все snapshots дня на UID; `interval_hint` не используется планировщиком. Даже после починки limiter 1000 UID при 30/min требуют не меньше примерно 33 минут для одного прохода одного потребителя квоты, а не обещанных 5 минут. Рассчитать capacity, batch/caching и показать действительную свежесть.
